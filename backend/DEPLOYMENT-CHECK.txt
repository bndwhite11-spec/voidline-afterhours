SHARED SERVICE / V7 VERIFICATION BOUNDARIES

The existing v6 Site was synchronized from its hosted source repository before
editing. Its source declares D1 binding DB and an ESM Worker; native database
overview confirmed the six v6 tables exist in production. Existing Site ID and
public audience remain unchanged by this upgrade.

The v7 source adds generated schema-only migrations:
  drizzle/0001_absent_pete_wisdom.sql
  drizzle/0002_watery_starhawk.sql

  drizzle/0003_famous_living_tribunal.sql
The original 0000 SQL, snapshot and journal entry remain unchanged. New tables
hold reactions, personal bookmarks, favorites, read positions and change events.
Added columns have constant defaults or are nullable. New indexes support
message revision lookups and thread/reply references as history grows. No data backfill or
request-time schema mutation is used. The build copies the complete migration
chain and metadata to dist/.openai/drizzle for supported Sites deployment.

SOURCE VERIFICATION
node backend/test.mjs: 24 SQLite contract checks, including the real generated
migration chain, ownership/moderation, exact thread references, durable retries,
change propagation, rollback, bookmarks, punctuated mentions and activity reads.
node backend/review-test.mjs: independent retained-data, access loss, deletion,
search, read-cursor and cross-account privacy review checks.

The source uses the existing supported project build script when managed helper
files are unavailable. Shared message text and metadata remain in D1. R2 is not
provisioned, so shared attachments and live voice/video are not advertised.

PUBLICATION
Generate offline/source downloads after all client edits, then build the Worker.
Package authored source and matching Worker/migration outputs, push the existing
Sites source branch, save that exact source SHA, then deploy to the existing
public Site. Hosted migrations run before Worker upload; a later deployment
failure can still leave applied migrations, so inspect status before repair.
Never change the immutable applied migration history.

EVIDENCE LIMITS
Source/SQLite tests use synthetic identities. No two independently authorized
signed-in accounts were supplied for this upgrade. No messages were sent to
real contacts. Browser/mobile screenshots, hardware media and actual visual
flows require the supported browser tool. The final delivery report must state
whether that tool and those accounts were available rather than imply that
Node or SQLite checks provide equivalent proof.

After publication verify terminal native deployment status and the literal URL.
When supported, verify the hosted health endpoint and authorized sign-in path.
A successful public page/health response does not independently prove a full
member-to-member exchange. A separate two-account test should cover invitation,
both directions of messaging, edit/delete/reactions, bookmarks, reconnection,
permission revocation and history, with isolated test communities.
