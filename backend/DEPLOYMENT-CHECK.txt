SHARED SERVICE RECHECK / TRUST EDITION

The live Site remains a static, owner-private client. Its native database
overview reports bindings:[] and tables:[] with no omissions. There is no
existing D1 binding or populated hosted schema to connect this UI to.

The supported Worker ESM output convention is known: a default fetch export at
dist/server/index.js and the Site manifest without static.directory. A local
review-only bundle serving static files plus worker/index.mjs was built and
smoke-checked: static request200, missing identity401, identity with no DB503.
This proves Worker hosting is possible, not that shared chat is available.

The exact missing setup remains:
1. The supported non-null D1 hosting-manifest binding declaration.
2. Sites migration manifest/journal emission and schema deployment pipeline.

Storage guidance describes automatic D1 provisioning from manifest/schema
metadata, but available starter manifests show only d1:null/r2:null. The Sites
setup/build/workflow helpers and Drizzle configuration are absent from this
execution image; associated binding/plugin/migration-emitter resources cannot
be read at their supplied paths. Native DB tools are read-only and expose no
provisioning, SQL-write, or migration operation. We did not guess a declaration,
create schema in request handlers, or publish a Worker that would only return
backend_not_configured. Durable Objects would need another unsupported binding
and migration declaration; they are not a verified workaround here.

Once that supported deployment setup is supplied, use the existing SQL-backed
API contract and tests, preserve platform identity, enforce membership on the
server, connect the client transport, and test separate authorized accounts.
Current SQLite tests use synthetic platform identity headers. A second person
also needs explicitly authorized Site access; no audience or invitations were
changed during this work. No live two-account milestone is claimed.
