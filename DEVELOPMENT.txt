IDENTITY AND AUTHORIZATION
- Immutable account IDs are the permission keys. Usernames normalize to unique
  NFKC/lowercase ASCII handles; display names, emails, provider subjects and
  community nicknames are separate fields. Matching @xrp never grants authority.
- A new account has zero joined communities, contacts, conversations, messages,
  gifts, earned badges and unread activity. Empty/default reads must not seed
  fixtures or resurrect samples after refresh. Preserve existing real records.
- Passwords use pinned @noble/hashes Argon2id v19, 19 MiB/two passes/one lane,
  random 32-byte salts and 32-byte output. Known legacy PBKDF2 records upgrade
  only after successful verification through a credential-version CAS. Do not
  weaken the algorithm to conceal runtime CPU constraints. Local workerd hash
  compatibility was checked; hosted capacity and production load remain gates.
- Secure HttpOnly __Host- cookies carry opaque server sessions. Signed-in writes
  validate Origin, CSRF, active session/status and expected account ID. Recovery,
  password changes, revocation and suspension invalidate prior access. Reject
  stale credential/session races. Keep secrets out of responses and exports.
- Google OIDC is real optional code/state/nonce/PKCE verification using jose;
  absent GOOGLE_CLIENT_ID/GOOGLE_CLIENT_SECRET/VOIDLINE_ORIGIN means unavailable.
  Provider email matches never link other accounts or publish provider identity.
- Verified-email recovery requires RESEND_API_KEY, EMAIL_FROM and trusted origin.
  Hash 256-bit one-use tokens, expire at ten minutes and consume atomically.
  Offline recovery codes are a separate explicit possession factor. A delivery
  API acknowledgement is not a received email. Never reveal an old password.
- SimpleWebAuthn verifies actual signed-in step-up; it is not standalone passkey
  login. Owner actions need recent authentication plus user verification. Never
  accept a client MFA flag. Challenge replay, expiry, origin/RPID and counters
  are server checked. Removing keys clears MFA; protect the owner's final key.
- No production owner was verified/bound by the upgrade. Follow
  docs/OWNER-BOOTSTRAP.md: signed-in proof, fresh passkey, short-lived private
  claim and trusted operator binding to an exact immutable ID. Then remove
  bootstrap secrets. Community ownership never implies platform administration.

MESSAGE, VAULT AND MEDIA BOUNDARIES
- Native D1 history is permission-checked Standard messaging, with explicit
  server-stored-text consent. Never label it E2EE or use it as an encrypted
  room fallback. Creating a native
  community does not create a Matrix room. Native friend/block/moderation rules
  are not yet mapped to independent Matrix identities and room permissions.
- Matrix JS SDK 45.1.0 / Rust crypto WASM 18.9.2 implement the protected path.
  Require configured homeserver, real whoami/device identity, encrypted room,
  current membership and verified devices. Verify authenticity shields before
  exposing decrypted content. Never invent a protocol or shared frontend key.
- Stable transaction IDs and encrypted intended outbox records precede SDK send.
  Acknowledgement means homeserver persistence, not delivery/read receipts.
  Payload conflicts fail. An old unconfirmed transaction needs its original
  Matrix token because deduplication is session scoped. Attachment retries use
  retryPending descriptors rather than resending a filename as text.
- Drafts and outbox are scoped to account/device/room/thread. Reserve revisions
  before awaits and serialize encrypted writes. Wrong passphrases, failed writes
  and old responses must preserve newer text and never claim a durable save.
  Background updates preserve composer node/caret and keyed message rows.
- Rust WASM Matrix-v2 attachments encrypt up to 8 MiB before upload. File keys,
  original names and descriptors travel inside encrypted message content. Use
  authenticated media requests; never put credentials/keys in URLs. Revoke local
  decrypted Blob URLs on close, navigation and account lock. Microphone access
  starts only on explicit action; late permission results stop all tracks after
  cancellation/account changes. Voice recording is limited to 60 seconds.
- This-device Saved works independently of Matrix. Its separate 16+ character
  passphrase derives AES-256-GCM through WebCrypto PBKDF2-HMAC-SHA256/600,000;
  fresh IVs and authenticated account/record namespaces protect stored content.
  Web Locks prevent concurrent writers. Passphrases/keys remain in memory.
  Metadata/counts remain observable in a browser profile. This is local at-rest
  encryption, not E2EE, cloud sync or recoverable account storage.
- Saved scopes are explicit: this-device notes, encrypted Matrix self-room and
  legacy references. Recheck membership/source access for bookmarks, searches,
  source jumps and downloads. A saved reference never bypasses permissions.
  Encrypted search covers only loaded decrypted history; no plaintext upload.
- There is no configured Matrix service/live two-device acceptance in this
  upgrade. Full native-to-Matrix community integration, encrypted-history index,
  complete encrypted-service moderation/retention, live voice/video/screen share
  and push delivery remain engineering/infrastructure work. Follow
  docs/ENCRYPTION-DECISION.md and docs/ENCRYPTION-THREAT-MODEL.md.

APPLICATION DATA AND MIGRATIONS
The complete 0000–0007 migration chain creates 47 application tables. Additive
0006_hard_tombstone.sql adds account lifecycle, passkeys/email tokens, verified
owner/audit/report records, organization/folders/targets/timeouts, profile privacy,
earned badge definitions/awards and concrete gift instances/transfers/showcases.
Older account IDs, memberships, histories and legitimate cosmetic ownership are
retained. Local archive ownership claims remain untrusted and are never used to
mint official items or privileges. Account deletion tombstones/anonymizes shared
provenance while clearing private state; owner/community-owner safeguards apply.

Keep SQL parameterized, page reads safely and enforce object access on every
API. Commit related mutations and audit events atomically. Retried folder,
message and gift operations need stable client IDs and conflict fingerprints.
Gift transfer acceptance checks current ownership, reservation, eligibility,
blocking and suspension again at commit time; clear the former owner's showcase.
Nine free decorations, twelve gift designs, earned awards and actual role
indicators have distinct semantics. Private gift notes remain unavailable.

Edit db/schema.ts intentionally, run npm run db:generate, review the new SQL,
journal and snapshot, then retain them unchanged after application. Request
handlers never create/alter migration-owned tables. Sites applies pending
migrations to managed DB before Worker publication. Local D1 and hosted D1 are
separate; use every migration in order for isolated test/preview databases.

BUILD, CHECK AND RELEASE
Use Node >=22.13 (Node 24 used here), Python 3 and the lockfile:
  npm ci --no-audit --no-fund --cache /tmp/voidline-npm-cache
  npm run test:foundation
  npm run test:server
  npm run test:client
  python3 -m pip install -r requirements-backup.txt
  npm run check:restore

The server runner discovers current backend/*-test.mjs suites. Historical v7
backend fixtures remain separately runnable with node backend/test.mjs and
node backend/review-test.mjs; they are not current auth/E2EE acceptance evidence.
The client runner includes retained archive regressions and controlled production
entry/extension cases. Focused checks can run directly, for example:
  node tests/voidline-home-test.cjs
  node backend/auth-hardening-test.mjs
  node backend/passkeys-test.mjs
  node backend/secure-messenger-test.mjs
  node backend/secure-media-test.mjs
  node backend/secure-vault-test.mjs
  node backend/local-saved-test.mjs

Build order matters because downloads include the current generated clients:
  npm run build
  python3 build_offline.py
  npm run build
  node scripts/check-build.mjs

The first build bundles passkeys/Matrix/WASM and creates Worker runtime output.
The offline/source packager then captures current authored/generated clients;
the second build embeds the fresh downloads into the final Worker asset map.
Exports exclude dependencies, caches, runtime DB/secrets and recursive build
output. check-build imports the actual generated Worker and checks served bytes,
HEAD/ETag, hidden paths, migration packaging and the preserved Site identity.
It does not run an interactive browser or verify external providers.

Use the supported Sites preview daemon when managed browser controls exist:
  sites-preview start /workspace/work/voidline
The npm dev adapter is Wrangler/local D1 under that workflow, not mock auth.
Publish through Sites source/package/deploy with the existing project ID,
audience and DB binding. Preserve a protected pre-release snapshot when trusted
provider export access is available. Never blindly roll code back to v10 after
Argon2id credentials have been written: that Worker cannot verify the new hashes
and does not enforce suspension. Prefer a forward-compatible fix that preserves
additive schema and IDs. A coordinated snapshot/code restoration needs isolated
compatibility checks and trusted provider controls; no destructive downmigration
is supported. Runtime credentials belong only in the server secret/configuration
store. docs/BACKUP-RESTORE.md and scripts/backup-db.py document sealed snapshots
and isolated restoration. Local restoration is verified; provider export,
production restore and backup scheduling require authorized infrastructure
controls and have not been performed by this upgrade.
